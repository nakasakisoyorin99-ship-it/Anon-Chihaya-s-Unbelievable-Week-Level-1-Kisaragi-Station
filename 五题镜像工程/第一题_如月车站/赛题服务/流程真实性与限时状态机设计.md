# 第一关流程真实性与限时状态机设计

状态：设计稿，尚未实现。目标是保证同一轮挑战的顺序和限时校验，不是识别人类或阻止AI。

## 一、服务端状态

以玩家身份下的当前轮次为权威，不以论坛窗口或浏览器脚本为权威。

状态：PREPARE（观察）→ ACTIVE（进行）→ SOLVED（通过）或 EXPIRED（超时）。EXPIRED通过显式重试创建新轮次，不把旧轮次改回ACTIVE。

数据建议：
- playerId / sessionId：玩家与会话绑定。
- roundId：随机轮次ID。
- startedAt、deadline：仅服务端记录；首次启动deadline=startedAt+240秒。
- status：PREPARE / ACTIVE / SOLVED / EXPIRED。
- privilegeGrantedAt、privilegeRoundId：本轮有效的升权记录。
- reportReadAt、reportReadRoundId、reportId：本轮读取报告详情记录。
- roundProof：本轮随机验证凭据，与比赛FLAG分开。
- solvedAt、result：成功记录及幂等返回结果。
- requestId / retryRequestId：启动和重试幂等键。

当前身份role仍保留赛题故意设计的批量赋值漏洞；其他字段必须为服务端内部字段，不能被资料更新POST修改。

## 二、操作规则

### 准备阶段

- 可读公开帖、账号资料及正常保存资料。
- 可以发现甚至验证role字段被错误接受，但没有正式轮次的升权证明。
- 报告列表和详情均返回423 challenge_not_started，不返回标题、路线、FLAG或本轮凭据。
- 仅访问论坛、读资料或开关面板不创建deadline。

### 剧情触发开始

前端在玩家越过呼叫柱的指定台词/舞台描述后调用POST /api/game/start。

事务内：
1. PREPARE：创建roundId，写一次startedAt/deadline，重置role=member，清空本轮升权与阅读记录，生成roundProof。
2. ACTIVE：返回既有轮次状态，绝不延长deadline。
3. SOLVED：返回已有成功状态，绝不新开一轮。
4. EXPIRED：返回410，必须显式重试。

重要：启动时重置身份会使提前升权只具有探索价值；正式解题必须在窗口内重新完成升权。

前端剧情是展示约定。用户能调用同样的API，所以不能宣称后端能证明其真的读过对白。不用简单“剧情token”包装这个事实。

### 活跃阶段升权

POST /api/forum/me保留接受role的预期漏洞。在ACTIVE且now<deadline时，role从member变为admin，记录privilegeGrantedAt和当前roundId。

- 输入验证全部完成后再写入，不能逐字段半成功。
- 不允许客户端写roundId、deadline、reportRead、solved等内部字段。
- 超时后拒绝产生有效升权记录；普通昵称/简介编辑是否继续允许不影响轮次认证。

### 阅读报告

列表与详情使用同一个状态门：
1. PREPARE返回423。
2. ACTIVE且now>=deadline：转EXPIRED，返回410，不泄露报告。
3. ACTIVE但非admin或privilegeRoundId不是本轮：403。
4. 条件满足：返回报告。

只有GET /api/forum/reports/71详情成功读取才记录reportReadAt及roundId，读取列表不算完成。记录语义是“服务器允许并返回报告”，不能证明客户端实际阅读了文字。

SOLVED可允许只读复盘，不再产生新阅读凭据。EXPIRED不能通过缓存命中服务端继续取答案；已经下载到客户端的信息无法撤回。

### 提交线索

请求：flag、platform、signal，加roundId和roundProof。后两项是同轮凭据，不是新增独立谜题。roundProof放在受限报告中，客户端读取后提交，绝不公开于状态接口。

读取并解析请求体完成后，在原子提交事务内用服务端now重新检查：
- 当前轮次为ACTIVE，roundId一致，now<deadline。
- 当前身份admin，privilegeRoundId一致。
- reportReadRoundId一致，reportId=71。
- startedAt <= privilegeGrantedAt <= reportReadAt <= now < deadline。
- roundProof、动态比赛FLAG、站台和提示音匹配。

成功一次性写SOLVED、solvedAt和结果；重复提交同一已通过轮次返回同一结果。错答422，不加时、不清空合法阅读记录。

截止边界明确采用“完整请求体读取并解析后，事务校验时刻必须早于deadline”。先检查时间再await读请求体不可接受。

比赛平台FLAG仍由GZCTF注入，不改成roundProof。若FLAG被提前获得，平台可能允许直接提交，游戏无法独立保证平台计分严格遵循故事流程；需要平台协作才能声称这一点。

## 三、刷新、重试和并发

- GET state永不写startedAt/deadline，不提供剩余时间或截止时间。
- 刷新、读档、论坛开关只恢复当前轮次；前端保存的日期和进度不参与认证。
- 请求重试携带相同requestId，服务端返回同一结果。
- POST retry只允许EXPIRED，并核对expectedRoundId；事务生成新roundId，重置身份、阅读记录和roundProof。
- 并发双击retry只产生一轮；迟到的旧请求因roundId失效，不能修改新轮次。
- 多标签页共享玩家当前轮次；一个标签页开启，其他页不能覆盖deadline。
- 截止时间无需高频后台定时器，每次操作依据deadline惰性判断；前端低频state查询只用于及时表现结局。
- 使用SQLite事务保存轮次、会话和结果，部署持久卷并恢复；进程重启不自动加时。若使用绝对时间，应保障宿主机时钟同步，不根据前端时钟裁决。

## 四、身份边界

只绑定Cookie能保证同一Cookie下刷新不加时，不能防清Cookie、隐身或换浏览器创建新身份。

- 若每队有独立GZCTF容器，可把当前轮次绑定到容器内队伍实例，Cookie只用于浏览器会话；该模式会让同队标签页共享轮次。
- 若多人共用服务，需要平台可信玩家身份（由服务端验证的票据），不能信任用户自行填写的teamId。
- 无平台身份时明确承认新会话可从头开始，不能称“所有刷新/换浏览器均不可重开”。

本项目推荐优先确认独立队伍容器部署方式；不擅自假定现有服务已经拥有可信队伍身份。

## 五、当前代码缺口

1. start只写deadline，未重置提前取得的admin，因此不保证窗口内升权。
2. 报告接口只检查deadline不为空，未拒绝已超时访问。
3. reportRead是布尔值，缺少时间、reportId和roundId绑定。
4. submit在await readJson前检查时间，可能允许截止后完成的请求。
5. retry缺少轮次预期值和幂等键，并发/迟到请求没有明确隔离。
6. 状态仅存Map，服务重启丢失；Cookie可被清除以取得新会话。

## 六、验收用例

- member/admin在PREPARE都取不到报告内容。
- PREPARE提前admin，start后恢复member；旧读取/凭据无效。
- ACTIVE正常POST→读71详情→提交通过。
- 只读列表、未升权、未读详情、旧roundId、旧roundProof均拒绝。
- 提前发提交请求但截止后才完整接收，拒绝。
- deadline前1ms可通过，等于deadline拒绝。
- 超时后POST 升权、报告列表/详情、提交都无法形成有效通关。
- 错答与重复start不改变截止时间；关闭/刷新/读档不改变轮次。
- 双start、双retry、并发成功提交只产生一次状态转换。
- retry后所有旧请求都不能污染新轮次。
- 服务重启后截止时间不变；接口不返回时间值、内部证明或未同步答案。

实施优先级：先修启动身份重置、报告过期门与提交截止复查；其次补轮次绑定和原子重试；最后持久化及平台身份联动。前两项应一并完成再宣称保证完整同轮流程。
